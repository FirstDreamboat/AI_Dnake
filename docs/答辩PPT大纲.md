## 逐页大纲

### P1 封面
- **标题**:AI 驱动的研发质量前置平台
- **副标题**:从需求体检到测试用例自动生成
- **团队**:测试部 · 大梦一场 · 办公效率赛道
- 讲词:"各位评委好,我们做的不只是一个测试用例生成器,而是把质量前置到需求阶段的研发基础设施。"

### P2 痛点(用数字扎心)
- 测试用例编写占测试部 **60% 工时**
- 但根因不在测试——**需求不清**,用例写再多也白搭
- 现状:PRD 写完→研发开发→测试提测才发现需求歧义/边界缺失→**全链路返工**
- 一句话:"问题在测试,根因在需求;补救在提测后,成本在提测前"
- 讲词:"我们算了笔账:一个需求返工平均消耗 3 个角色各半天。如果提测前就能发现需求缺陷,这笔账就省了。"

### P3 我们的方案(一句话定位 + 全景图)
- **一句话**:不是给测试加工具,是把质量前置——产品自检需求、研发提测自带用例、测试专注探索
- **全景图**(一张图):需求文档 → [需求体检] / [测试点提取] → [用例生成] → [评审] → [脚本] → 知识库沉淀
- 讲词:"左边是产品上传 PRD,中间是 AI,右边输出体检报告和可执行用例。三个角色各取所需。"

### P4 核心能力①:需求→用例 全流程
- 全流程闭环:需求解析(多格式)→测试点提取(六类)→用例生成(编号规则)→评审(质量评分+AI补全)→脚本生成
- 支持 md/txt/docx/pdf/**图片原型/Axure .rp**
- 讲词:"这是基座能力。重点不是'能生成',而是'生成得专业'——下一页讲。"

### P5 核心能力②:设计技术标签化(差异化亮点)
- 每个测试点标注**设计技术**:等价类/边界值/判定表/状态迁移/场景法/正交表/错误推测
- 不止按"类型"分,还按"方法"分——**覆盖度多维分析**
- 边界值类必须覆盖上下界、等价类必须有效+无效各一条——**让方法论指导取值**
- 讲词:"通用 AI 生成用例是'凭感觉',我们让测试设计方法论真正进 prompt。"

### P6 核心能力③:需求质量体检 ★重点★(影响面拓展)
- 上传 PRD → **30 秒出体检报告**:评分 + 问题清单(歧义/缺失边界/流程断点/异常未定义/隐式场景过多)
- **实测案例**:登录注册 PRD → 52 分,22 项问题
- 真实发现:需求里"未勾选协议"一条写"按钮拦截"、一条写"按钮置灰",**自相矛盾**——这种不到提测没人发现
- 讲词:"这一页是关键。它证明平台不只服务测试部——**产品上传 PRD 就能用**。影响面从 20 人扩到全研发链条。"

### P7 技术架构(给技术评委看深度)
- **LLM + RAG + 多智能体**:需求解析/测试点提取/用例生成/用例评审四 agent 协同
- **视觉模型 Qwen3-VL**:解析原型图/设计稿为结构化需求
- **向量库 BGE-M3**:知识库语义检索,云端优先+本地兜底
- FastAPI + Vue + MySQL,工程化落地
- 讲词:"不是套壳。四套模型协同,还有测试方法论注入。这是工程深度。"

### P8 现场演示 ★重点★(3 分钟,定名次)
- **演示 1:需求体检**(90 秒)
  - 切到产品经理账号 → 上传「登录与注册.md」→ 30 秒出 52 分报告 → 指着"未勾选协议矛盾"那条讲
- **演示 2:用例生成**(90 秒)
  - 切回管理员 → 选项目 → AI 生成 → 展示测试点(带设计技术标签)+ 用例 + 一条生成的脚本
- 数据预跑好,现场不实时生成(防翻车)
- 讲词:"我切到产品经理账号——产品登录看到的就是需求体检。上传,出报告,52 分,这一条矛盾需求揪出来了。"

### P9 数据与成效(用真数字说话)
- 真实数据:**2000+ 测试点、35 份真实需求文档**(楼宇对讲/智能家居/中控屏)
- 提效对比:某需求,人工 20 条用例 2 小时 vs 平台生成+微调 10 分钟
- 知识库:3 篇文档 772 chunks 向量化,混合检索可用
- 讲词:"不是 demo 玩具,是真实业务跑出来的。这些数据都在库里,可查。"

### P10 多角色协作(影响面再强化)
- 5 个角色:管理员/项目经理/测试工程师/**产品经理/研发人员**
- 同一平台,三拨人各取所需:
  - 产品→需求体检
  - 研发→需求体检 + 提测脚本
  - 测试→全流程用例生成
- 讲词:"一个平台,三种视角。这就是研发质量基础设施的含义。"

### P11 创新与差异化(防评委问"和别人有啥不同")
- ① **嵌入式垂直场景**:懂楼宇对讲/智能家居/中控屏的测试方法论,不是通用模板
- ② **设计技术标签化**:让测试设计方法论进 AI,而非凭感觉生成
- ③ **需求质量体检**:从"生成用例"升级到"需求前置体检",影响面扩到全研发
- ④ **三方对照 UI 走查**(已验证可行,待工程化):原型图+需求文本+APP 截图

### P12 展望(展现可持续性)
- 短期:UI 走查模块工程化(原型 vs APP 自动对比,已验证链路通)
- 中期:执行闭环(生成→在线运行→报告)
- 长期:质量数据反哺产品迭代
- 讲词:"这不是终点。我们已经验证了 UI 走查可行,下一步让它真正闭环。"

### P13 总结(价值回归)
- 把质量**前置**到需求阶段
- 把测试**方法论**注入 AI
- 把平台**扩展**到全研发链条
- 一句话:"我们做的不是工具,是让质量在源头发生。"

## 评委可能问的 + 答案要点

| 问题 | 答案要点 |
|---|---|
| "和直接用 ChatGPT 生成用例有啥区别?" | ① 嵌入式垂直场景+测试方法论注入(设计技术标签) ② RAG 历史知识增强 ③ 全流程闭环+评审,不是单次生成 ④ 落库管理可追溯 |
| "需求体检准确率多少?" | 登录注册 PRD 实测揪出 22 项,其中"未勾选协议矛盾"经人工核对属实。准确率用真实需求验证,不是刷榜数字 |
| "研发真的在用吗?" | 已具备能力(演示可见),正在向研发/产品推广;有 1-2 个同事已试用(若真有就说) |
| "AI 生成的不靠谱怎么办?" | 有评审智能体打分+AI补全+人工反馈闭环;ai_reviewed 状态标注,不直接采信 |
| "断网怎么办?" | 演示数据预跑好;生产可切本地 Ollama(已支持云端优先+本地兜底) |
| "成本?" | 硅基流动免费额度覆盖;本地部署零 API 成本 |

## 三个雷区(务必避开)

1. **别现场实时生成**——联网依赖,断网/限流就翻车。数据预跑好,只演示"点按钮看结果"
2. **别把需求体检说成已服务全公司**——讲成"已具备能力、正在推广",有演示实证就不算吹
3. **别只讲测试**——开场就把定位拉到"研发质量前置",否则评委会按"测试部工具"低估影响面
